# 0.2.0 transition decisions and implementation map

Status: maintainer policy accepted; implemented in the v0.2 integration candidate. Release review and publication remain separate. The original consolidated wording is preserved in Git at `10d572b`; this file now records the decisions and points to the effective guides instead of maintaining a second competing policy draft.

## Recorded maintainer answers

The following answers were recorded on 2026-09-10. The original “documentation consequence” column records the preparation-stage handoff; follow the implementation map below for current source terms and behaviour.

| ID | Question | Recorded answer | Documentation consequence |
| --- | --- | --- | --- |
| Q1 | Does free access rule out donations or paid support? | The editor and all its features stay free and open source; voluntary donations or paid support may sustain development. | Describe support as optional; do not suggest that payment unlocks features. |
| Q2 | How strong is the standalone-app commitment, and is it required for 0.2.0? | An aspiration to explore when capacity permits. | No promised delivery date, 0.2.0 prerequisite, or guaranteed parity. |
| Q3 | Which future desktop platforms should we name? | Ubuntu first, macOS second, Windows last. | State this priority order; distinguish Ubuntu validation from Linux-wide support. |
| Q4 | Which distribution channels are required for 0.2.0? | GitHub releases first; Marketplace and Open VSX remain later goals. | Link to actual GitHub releases and avoid announcing listings before they exist. |
| Q5 | What support should development builds receive? | Welcome reports from identifiable commits, investigate as capacity permits, and normally fix current development; no response-time guarantee. | Retain reports from older commits without promising maintenance of every historical revision. |
| Q6 | Which AGPL version policy should the separate licensing work implement? | `AGPL-3.0-or-later`. | Use this exact identifier in the licensing handoff; operative files change separately. |
| Q7 | What should the branding policy permit? | Community builds and references may use the artwork while clearly distinguishing themselves from official releases. | Prepare permissive community-use wording; exact artwork terms are implemented separately. |
| Q8 | Should we promise not to offer a proprietary editor edition? | Commit to the open-source edition without ruling out future licensing arrangements. | Do not promise never to consider alternative licensing; retain the Q1 commitment to free, open-source feature availability. |

The workstreams converge through `codex/0.2.0-integration`: export, release identity, documentation and VSIX automation. Component merges preserve focused history. The final integration PR to `main` is the maintainer's review boundary; it does not publish a release.

The earlier 682-pass/4-skip/4-fail browser result was a historical failed run. Its defects were investigated and corrected before integration; retain the dated export record instead of presenting that result as the current candidate state. New package/dependency changes require their own validation and do not inherit acceptance from an older VSIX.

Routine implementation details may change within these contracts. Changes to license policy, official support promises, platform scope, source capture, output overwriting or dependency distribution need an explicit updated decision and matching evidence. An implementation can be ready for review without being accepted, merged or released.
