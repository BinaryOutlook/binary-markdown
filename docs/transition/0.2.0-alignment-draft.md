# Binary Markdown 0.2.0: consolidated transition draft

Status: **Maintainer policy answers recorded; public wording remains a draft.** Prepared 2026-09-10 on `codex/0.2.0-transition-docs`, based on `main` at `9ff6ce0`.

This document collects the agreed policy direction, proposed public wording, documentation structure, and remaining implementation dependencies in one place. It does not announce a release, amend a license, change contribution terms, or establish a new support guarantee. The effective terms remain in [LICENSE](../../LICENSE) and [CONTRIBUTING.md](../../CONTRIBUTING.md).

## 1. Agreed direction and branch responsibilities

The 0.2.0 initiative brings together the export subsystem, a planned AGPL transition, the project-supplied `01 / MD` logo, and clearer ways to build and contribute between official releases.

Binary Markdown should remain a free, open-source Markdown editor. A standalone desktop application is a long-term aspiration to explore when capacity permits, with Ubuntu first, macOS second, and Windows last. The public statement should express that aspiration without claiming a delivery commitment, a measured percentage of shared code, or feature parity that has not been demonstrated.

| Workstream | Responsibility |
| --- | --- |
| `export-subsystem` | Export implementation, acceptance evidence, and the separate licensing preparation agreed by the maintainer. |
| `codex/0.2.0-transition-docs` | Draft the project statement, release/build/support policies, attribution and branding guidance, licensing rationale, and transition communication. |
| Subsequent implementation work | Actual license/manifests/contribution-term changes, logo installation, build-information tooling, packaging fixes, and CI changes. Their implementing branch must be explicit. |

The documentation branch does not modify application code, package metadata, operative license terms, icon assets, or workflows. Publication and merging are later actions. During parallel work, the export branch remains authoritative for its specification and validation records.

## 3. Project identity and long-term statement

### Proposed README introduction

Binary Markdown is a free, open-source visual Markdown editor, independently maintained by BinaryOutlook. It builds on Any Markdown by raggbal and contributors, whose MIT-licensed work provides the foundation for this project.

We want writing in Markdown to remain accessible, dependable, and open to improvement by its users. The source is part of the product: you are welcome to inspect it, build it, adapt it, and contribute to its development under the applicable license.

### Proposed long-term statement

Our ambition is for Binary Markdown to become a free, open-source Markdown editor you can choose with or without VS Code. As capacity permits, we would like to explore a standalone desktop application alongside the extension, building on the shared editor foundation so that improvements can benefit both experiences.

We want to earn a place as your preferred Markdown editor through reliable editing, useful features, and continued openness. Our intended desktop priority is Ubuntu first, macOS second, and Windows last. A standalone release is not a prerequisite for 0.2.0, and we are not announcing a delivery date or feature parity. Platform availability and feature support will be published as the work is implemented and validated.

### Proposed sustainability statement

We are committed to keeping the editor and all its features available in the free, open-source edition. Voluntary donations and paid support may help sustain development; they do not unlock editor features. We are not ruling out future licensing arrangements, provided the commitment to the open-source edition is preserved and the project has the necessary rights.

### Evidence boundary for this statement

The current repository contains an Electron application and shared editor assets. Its [package](../../electron/package.json) includes desktop build configuration, and its [host bridge](../../electron/src/preload.ts) shows platform-specific behaviour. Those facts establish a foundation, not complete parity or a current standalone release commitment. In particular, the export branch defers Electron export. Do not describe a "supermajority" of shared code without a defined and measured basis.

### Proposed roadmap wording

For 0.2.0, our focus is the VS Code extension: integrate and validate document export, prepare the AGPL transition, adopt the new identity, and improve the source-build experience. When capacity permits, we would like to evaluate standalone readiness on Ubuntu, then macOS, then Windows. Each step should identify what already works, what host-specific development remains, and what evidence is needed before a release. Marketplace and Open VSX distribution can follow the initial GitHub release independently of standalone development.

## 4. Releases, branches, and support

### Proposed public policy

Binary Markdown is proudly open source. Official releases are published periodically, when a set of changes has completed release validation; we do not promise a fixed release schedule.

You are welcome to build, study, and modify the extension between releases. For development builds, we recommend starting from `main`, where changes are integrated. Other branches may contain incomplete experiments. An unreleased build has not necessarily undergone the same validation as an official release.

Bug reports from development builds are welcome, even when the affected commit is not the latest release or the current tip of `main`. Please include the full commit ID, whether you made local changes, your environment, and clear reproduction steps. This helps us check out the same revision and investigate.

We will make a reasonable effort to reproduce and diagnose reported problems. We may ask you to test a newer commit, and fixes will normally land in current development rather than being backported to every historical revision. An older checkout may depend on tools or services that are no longer readily available; we will explain when that prevents reproduction.

Access to the source is central to this project. Building your own version is an intended way to use Binary Markdown.

### Proposed distribution statement

GitHub releases will be our initial official distribution channel for 0.2.0. VS Code Marketplace and Open VSX publication remain later goals. We will link to official listings when they exist; their absence does not prevent users from building the extension or installing a published VSIX.

### Proposed channel descriptions

| Source | How to describe it |
| --- | --- |
| Official release | A named, maintainer-published snapshot with matching source, package identification, and recorded validation. A prerelease remains explicitly labelled. |
| `main` | The recommended integration branch for development builds. Validation belongs to a particular commit and environment. |
| Feature branch | Work in progress; capabilities, installation, and tests may change before integration. |
| Community fork or locally modified checkout | Welcome within the applicable terms; identify its origin and modifications when distributing or reporting problems. |

Do not use "fully validated main" until actual merge gates justify the claim. Do not label an arbitrary locally built VSIX an official release merely because its package version matches one.

## 5. Building from source

### Proposed guide introduction

Choose the code you want to run: an official release tag for a published snapshot, `main` for integrated development, or a specific commit when investigating a report. Follow the instructions and license present at that revision.

Use a fresh directory and the Node.js version indicated by that checkout's `.node-version`. The inspected baseline specifies Node 20.20.0. Installing the extension from a VSIX does not require Marketplace publishing credentials.

### Draft command sequence

These commands are based on inspected repository scripts; this documentation task has not executed a fresh build. Recheck the complete guide on the integrated 0.2.0 candidate before publishing it.

```sh
git clone https://github.com/BinaryOutlook/binary-markdown.git
cd binary-markdown
git switch main
git rev-parse HEAD
npm ci
npm run package
```

For a particular revision, select it before installing dependencies. Replace `COMMIT_ID` with the full commit ID or `RELEASE_TAG` with a real published tag; these are placeholders, not literal names.

```sh
git checkout --detach COMMIT_ID
```

Or:

```sh
git checkout --detach RELEASE_TAG
```

Then run the dependency installation and packaging commands for that revision. The package script already invokes compilation. It writes a VSIX under `dist/`, named from that checkout's package name and version. Install it using VS Code's **Extensions -> Install from VSIX** action, reload if prompted, and select Binary Markdown for a Markdown document.

To return to a published version, install the chosen official VSIX. Avoid changing extension identifiers as part of ordinary local builds; installing the same identifier updates or replaces that installed extension. Use an isolated VS Code profile for testing when appropriate. Keep any personal document changes separately from a source checkout used for reproduction.

### Export prerequisites

On the export branch, HTML needs no additional converter; PDF uses an installed compatible Chromium-family browser; DOCX/EPUB use separately installed Pandoc. Native tools are user-managed. Link to the export help for supported hosts, discovery settings, and limitations. These are runtime export requirements, separate from merely packaging the extension.

### Build provenance implementation dependency

The existing [package script](../../scripts/package-vsix.js) ties installed documentation links to `v<package version>`. Community builds need links to the actual source commit, plus a way to retrieve their build identity. These are implementation tasks outside this branch. Until they land, document the manual commands below and keep the commit ID with the VSIX; do not advertise a nonexistent "Copy Build Information" command.

## 6. Bug-report and contribution drafts

### Proposed issue introduction

Reports from official releases, development commits, and community builds are welcome. A version number alone may not identify an unreleased build. Please provide the source revision and a small reproduction so we can investigate the same behaviour.

### Draft report fields

| Field | What the reporter should provide |
| --- | --- |
| Build source | Official release, `main`, named feature branch, or a community fork. |
| Revision | Full commit ID, release tag, or the best available build identifier. Explain if unknown. |
| Local modifications | Whether the checkout was modified; a relevant patch or description where possible. |
| Environment | Host editor/version, operating system, and architecture. |
| Reproduction | Minimal steps and a small Markdown example, with expected and actual behaviour. |
| Export context, if relevant | Format, Pandoc/browser versions, warning text, and relevant settings. |
| Logs or screenshots | Only the portions needed to demonstrate the issue. Remove private document contents and personal paths. |
| Retest, if available | Whether the issue also occurs on a newer commit; this is useful information, not a condition for initially reporting it. |

For a source checkout, these commands report its identity and tracked modifications:

```sh
git rev-parse HEAD
git status --short --untracked-files=no
node --version
npm --version
```

Mention relevant untracked files separately if they affect the build. Report Pandoc/browser versions for export issues. A clean checkout identifies tracked source but does not guarantee an identical runtime environment or byte-for-byte identical artifacts.

### Proposed contributor welcome

Contributions to code, documentation, translations, accessibility, testing, and bug reproduction are welcome. Focused changes with a clear purpose are easier to review. Describe what changed, how you checked it, and any known limitations. Building from source, investigating an older commit, and improving a reproduction are valuable contributions.

Contributors retain their copyright. The applicable contribution terms are the ones stated in the repository at the time of contribution. Any future AGPL contribution-language update must land with the operative licensing change; this draft does not replace the current MIT statement.

## 7. Planned licensing rationale and attribution

### Proposed announcement wording

For 0.2.0, we plan to transition continued Binary Markdown development to the GNU Affero General Public License, version 3 or any later version (`AGPL-3.0-or-later`). We are grateful to the original Any Markdown author and contributors, whose MIT-licensed work made this fork possible. Their attribution will remain part of the project.

Our aim is to preserve users' ability to inspect, modify, and share the software, including covered versions offered through network services. Commercial use remains permitted under AGPL's conditions; our objective is continued user freedom, rather than payment from downstream developers. AGPL does not require contributions to our repository. [AGPLv3](https://opensource.org/license/agpl-3.0)

Previously published MIT versions, including the existing export implementation, retain their existing permissions. The transition does not erase upstream ownership or independently licensed components. [MIT terms](https://opensource.org/license/mit)

### Information the final licensing guide must identify

- The first effective AGPL commit and release, using the selected `AGPL-3.0-or-later` policy.
- The preserved upstream notices and inventory of separately licensed components.
- Where recipients obtain matching source and build instructions; see [AGPLv3 section 6](https://opensource.org/license/agpl-3.0).
- The boundary between project software, exported user content, and embedded resources.
- The artwork and identity terms implementing the approved community-use direction from Q7.
- The outcome of the host-integration and dependency review, including any deliberately adopted exceptions.

Until these items are resolved and implemented, use "planned AGPL transition" rather than "now AGPL". "AGPL-ready" is a preparation status, not the effective license.

## 8. Logo and branding draft

### Proposed public introduction

Binary Markdown introduces its own `01 / MD` identity for 0.2.0. The new artwork distinguishes this project's releases while preserving acknowledgment of the Any Markdown code and contributors on which it builds.

### Preparation and implementation boundary

The maintainer supplied `BinaryMarkdown.png` as the chosen logo. Preserve that approved artwork, record its provenance without inventing authorship, and prepare appropriately sized extension and desktop assets in the implementation workstream. A supplied PNG is not an editable SVG; do not claim a vector original exists. Check small-size legibility and light/dark presentation before release.

The current acknowledgments identify the old icon as inherited. Update that sentence when the new assets actually replace it, and keep historical attribution in the archive. Q7 permits community builds and references to use the artwork, with clear distinction from official releases, subject to implementing the exact terms. We welcome community builds and factual references to Binary Markdown using the project artwork under its published terms. Clearly identify community builds as such, including the source revision and any modifications. Use of the project identity should not imply that a build was published, validated, or endorsed by the Binary Markdown maintainers. The final branding document should link directly to the artwork terms so users can find the applicable permissions.

This document does not grant new artwork permissions, assert a registered trademark, or change software-license rights.

## 9. Export documentation and current evidence

### Proposed short user-facing description

The planned 0.2.0 release adds experimental HTML, PDF, DOCX, and EPUB export. Save the named Markdown file, then choose a format from the export menu. HTML/PDF follow supported editor rendering; DOCX/EPUB favour editable document structure. Format-specific differences and fallback warnings are documented in the export help.

The present implementation targets local desktop VS Code on macOS and Linux. Recorded checks cover macOS ARM64 and Ubuntu x86-64. Windows, remote/web hosts, and Electron export are not established by that evidence. Update this statement only when new validation supports it.

### Evidence to preserve at convergence

The export branch at `35e7e48` records passing export checks and a broader Ubuntu browser result of **682 passed, 4 skipped, and 4 failed**. The full suite must not be described as green. Earlier package validation is tied to its own source and artifact; it does not automatically validate a repackaged 0.2.0 build.

Use the [pinned export validation record](https://github.com/BinaryOutlook/binary-markdown/blob/35e7e489306a1d5dd16020b8aae9713c353d1738/docs/export-validation.md) and [pinned user help](https://github.com/BinaryOutlook/binary-markdown/blob/35e7e489306a1d5dd16020b8aae9713c353d1738/media/export-help.md) while the branches remain separate. After integration, link to the files in the final release tree. Retain detailed evidence in the export workstream rather than duplicating it throughout the public guides.

## 10. Draft transition announcement and changelog

### Announcement for the preparation period

We are preparing Binary Markdown 0.2.0: document export, a new project identity, and a planned transition to AGPLv3 or later. The original Any Markdown project and its contributors remain an acknowledged part of our foundation.

We are also improving the experience of building between releases. Official releases will provide convenient, documented checkpoints, while development builds remain an intended way to use the editor. Reports from identifiable commits are welcome, including versions that are not the latest release.

Our long-term ambition extends beyond VS Code. As capacity permits, we would like to explore a standalone desktop application, prioritizing Ubuntu, then macOS, then Windows. This is an aspiration rather than a scheduled release commitment. We want to earn your preference through useful editing, reliable maintenance, and continued openness.
