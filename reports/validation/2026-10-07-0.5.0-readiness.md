[Validate VSIX run 37252328035](https://github.com/BinaryOutlook/binary-markdown/actions/runs/37252328035), a push run for the full inspected `main` commit, completed with **failure** on 2026-10-05. Current job results were inspected during this assessment:

The failure is `test/specs/selected-ui-ux.spec.ts`'s **expanded diagnostics expose the parser explanation and support keyboard scrolling without edits**. After End reached the lower boundary, Home did not return the diagnostic region to the top: the check expected `scrollTop` 0 and observed 964. This evidence identifies the failing assertion; it does not establish whether the cause is native keyboard behavior, focus handling or a timing defect. Do not dismiss it as flaky or rerun merely to obtain a pass.

On 2026-10-07, the same focused test passed once locally on macOS ARM64 using Node 24.21.0 and the unchanged runtime from this baseline: `CI=1 npx playwright test test/specs/selected-ui-ux.spec.ts --grep 'expanded diagnostics expose' --workers=1 --retries=0`. Compilation and standalone fixture generation passed first. The local server initially could not bind under sandbox restrictions; the test ran successfully after native-process permission was granted. This single-test observation does not explain the hosted failure or replace its required macOS shard.

This run's successful lanes validate its 0.4.1-versioned package at the inspected source. They do not establish release validation for a newly versioned 0.5.0 candidate. The final merged `main` must pass every named native lane and all nine browser shards, with package and evidence from the same run attempt.

## Review candidate

The first local review label is **0.5.0 RC1**, with numeric manifest version `0.5.0`. A local package remains a review build. Retain its `.vsix`, `.vsix.sha256` and `.vsix.build-info.json` together. The sidecar identifies its full source commit, clean/local-change state, build runtime and SHA-256; local builds have no GitHub Actions identity.

Use the [installation and checksum procedure](../../docs/building.md#inspect-and-install-the-output). The candidate delivery must also state its exact source, checksum, verification outcomes and limitations. After reload, compare **Copy Build Information** with the delivered sidecar. A replacement distributed candidate increments the review counter instead of silently replacing RC1.

## Focused acceptance checklist

Use synthetic documents or a backup, and record the exact candidate identity with each result.

- [ ] Move through Visual, Source and Split; edit and save, Undo/Redo, close and reopen. Confirm that source and current edits survive and that Split's preview is read-only.
- [ ] Find commands through the three-dot search, Action Palette and Insert workspace. Test narrow panes, keyboard navigation, Escape and retained insertion/selection locations.
- [ ] Search source with case, whole-word and regular-expression matching; replace selected matches and Undo once. Confirm that metadata and hidden syntax matches can be located in Source.
- [ ] Navigate a wide table, insert and undo rows/columns, resize the pane and change control placement. Check cell visibility and preservation of untouched table source.
- [ ] Copy long code with authored whitespace, toggle wrapping, switch views and save/reopen. Confirm exact source, visible wrap feedback and reset after reopening.
- [ ] Edit valid and invalid equations/diagrams, inspect diagnostics and scroll long details with keyboard and pointer. Investigate the recorded macOS Home failure before considering this check accepted.
- [ ] Exercise ordinary export and cancellation with the installed candidate; inspect representative HTML, PDF, DOCX and EPUB in actual readers. Record any carried-forward reader limits being accepted.
- [ ] Check an update from 0.4.1 retains settings, extension identity and default-editor associations; compare **Copy Build Information** with the candidate sidecar.

## Remaining release gates

1. Diagnose and resolve the macOS browser failure, or document a justified test correction with evidence. Preserve the required check rather than weakening it.
2. Complete candidate acceptance and acknowledge the retained parser, external-write and reader limits in the [version notes](../../release-notes/0.5.0.md#known-limitations).
3. Review and merge the alignment branch through required PR checks. It changes version manifests, so it requires full validation rather than the documentation-only PR fast path.
4. Validate the actual merged `main` commit and promote the exact successful candidate and all matching evidence using the [release procedure](../../docs/releases-and-support.md#maintainer-release-procedure).
5. Inspect the release draft and publish when accepted. Marketplace/Open VSX uploads and standalone installers are separate actions.
