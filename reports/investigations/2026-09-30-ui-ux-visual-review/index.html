Shared design language and review boundaries

Neutral surfaces, charcoal typography, one muted blue accent, thin dividers and compact labeled controls. Familiar system type; monospace for source. The provisional audience is students and developers writing prose, code, equations and tables. Supported themes and user preferences must remain intact.

CanvasRailTextAccent

Current screenshots use unchanged production markup, styles and scripts in a browser with synthetic documents and a mock host. Export capabilities and statuses are simulated. This is not an installed-extension, converter, reader or assistive-technology acceptance result.

All redesigns are static generated concepts. Written legends define the proposed scope when incidental generated text, counters, shortcut glyphs or chrome differs. Host status must be authoritative; no sharing, comments, AI, code execution or cell merging is proposed. Replaced earlier images are retained only for provenance.

Writing canvas and visual hierarchy

What the current UI shows

At 1280 × 720, the first heading starts about 126 px below the editor box top. The source gives the editor and Source view 100 px of top padding. Persistent corner width markers and blue section headings add emphasis outside the prose. Empty documents already show a writing hint; this proposal improves its placement and prominence rather than inventing a missing empty state.

Code-level evidence
  • Writing inset and reading width src/webview/styles.css:418
  • Source view inset src/webview/styles.css:445

Current visual

1 supporting current state

Preserve: Keep the existing width, alignment, outline and font-size preferences, Markdown content, scroll position and selection. Use an optional focus view rather than replacing the baseline.

1

Recommended

Generated concept
  1. Less empty space before writing: reduce the top inset while keeping a comfortable reading column.
  2. Quiet hierarchy: use charcoal headings and restrained section rules.
  3. Guides when useful: expose width assistance on focus rather than during ordinary reading.

Design rationale. A smaller top inset gives short panes useful writing space while retaining the familiar page and outline. Quiet typography makes document structure clear without competing with the content.

Practicality. Low to medium effort. Tune spacing at multiple pane widths; do not change saved width preferences.

2

Moderate

Generated concept
  1. Clear document and mode: add a compact filename and Visual/Source control.
  2. Comfortable reading measure: center the article and reduce rail width.
  3. Optional Focus: reduce distractions through an explicit user choice.

Design rationale. A document header clarifies the current file and mode. A narrower rail and optional Focus control provide stronger organization, with more layout work than the first option.

Practicality. Medium effort. Header and focus behavior need a host-aware file identity and explicit mode state.

3

Experimental

Generated concept
  1. Navigation on demand: use an optional collapsed rail.
  2. Formatting follows selection: move secondary tools close to the active text.
  3. Essential actions stay reachable: preserve visible Insert and Source access.

Design rationale. An optional focus workspace prioritizes sustained writing. Contextual tools reduce permanent chrome, but require careful keyboard access and selection behavior.

Practicality. High effort. Contextual positioning, focus recovery and discoverability need interaction prototypes.

Success criteria if implemented

These describe future acceptance; a generated image does not satisfy them.

  • At short and narrow pane sizes, the first editable line remains visible without scrolling.
  • Opening or closing navigation and width guidance preserves the selection and authored Markdown.
  • Empty-document guidance is readable and disappears at the appropriate time without adding document content.

  3. Destructive action in More.

Success criteria if implemented
